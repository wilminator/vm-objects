# Setting up Backblaze B2 for vmobj

B2 speaks the S3 protocol, so vmobj uses it like AWS: an `s3://` address
with B2's `endpoint=`. Two scripts set up and remove what vmobj needs:

- `scripts/b2/provision.sh` creates a private bucket with Object Lock, and
  an application key that can use only that bucket, written straight into
  a credentials file.
- `scripts/b2/teardown.sh` removes them again.

As with AWS, the same scripts make a throwaway **test** bucket and the
bucket for your **real backups**; `--purpose` decides how hard teardown
makes it to delete the bucket.

## What you need once

- **The b2 tool (version 4) and `jq`**, on the machine you run the scripts
  from (WSL is fine):

  ```bash
  sudo apt install -y jq pipx && pipx install b2
  ```

- **Sign it in** with your account's master key, or a key with every
  capability. It asks for the key ID and the key, so neither lands in your
  shell history:

  ```bash
  b2 account authorize
  ```

That key only runs the scripts. vmobj never gets it, and it should never
be copied to a NAS.

## What the scripts create

| Piece | Settings |
| --- | --- |
| Bucket | Private, Object Lock on, B2-managed encryption (SSE-B2). No default retention: vmobj sets each file's lock itself. The purpose and key name are stored in the bucket's info. |
| Lifecycle rule | Removes hidden (deleted) file versions after 1 day (`--keep-deleted-days`), and large uploads never finished after 7 days. B2 never removes a version that is still locked. |
| Application key | Named `vmobj-BUCKET`, limited to the bucket, with `listBuckets, readBuckets, listFiles, readFiles, writeFiles, deleteFiles, readBucketEncryption, readBucketRetentions, readFileRetentions, writeFileRetentions, readFileLegalHolds`. Not `bypassGovernance`, not bucket or key management: a leaked key can't remove a locked backup early or loosen the bucket. |
| Credentials | Written to `~/.aws/credentials` (or `--credentials-file`) as profile `vmobj-BUCKET`. The secret is never printed. |

B2 has one storage class. Back up to it with `--profile offsite` (nightly
backups, kept up to a year) or `--profile test` (tests); the archive
profiles are for AWS.

## A bucket for real backups

```bash
scripts/b2/provision.sh --bucket wilminator-vmobj --purpose backups
```

It prints the repository address, for example:

```
s3://wilminator-vmobj?endpoint=https://s3.us-west-004.backblazeb2.com&region=us-west-004&profile=vmobj-wilminator-vmobj
```

Make the repository under a prefix, with Object Lock:

```bash
vmobj init --object-lock --repo 's3://wilminator-vmobj/vmobj?endpoint=https://s3.us-west-004.backblazeb2.com&region=us-west-004&profile=vmobj-wilminator-vmobj' --key-file /path/to/vmobj.key
```

## A bucket for restic

restic deletes and rewrites its own files, so it can't work under locks:

```bash
scripts/b2/provision.sh --bucket wilminator-restic --purpose backups --no-object-lock --keep-deleted-days 30
```

Files restic deletes or replaces stay recoverable for 30 days (B2 keeps
the hidden versions). The key can still delete versions outright, so this
bucket is protected less than a locked one; the local snapshots and the
cold copy in AWS cover that.

## Carrying the key to the NAS

Write it to a separate file, copy that to the NAS, then delete it:

```bash
scripts/b2/provision.sh --bucket wilminator-vmobj --purpose backups --credentials-file ./b2-vmobj.credentials
```

## Removing a test bucket

```bash
scripts/b2/teardown.sh --bucket my-vmobj-test
```

A bucket provisioned as `backups` also needs `--destroy-backups NAME`.
